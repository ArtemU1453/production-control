## Развёртывание — Публикация тестовой версии на GitHub Pages

> Инфраструктура публикации, без изменений бизнес-логики, алгоритмов расчёта,
> моделей и пользовательских сценариев. Все правки dev-safe: поведение при
> локальной разработке и корневом деплое не меняется (`base` по умолчанию `/`).

### Способ публикации

GitHub Pages (проект полностью статический) + GitHub Actions — без сторонних
аккаунтов. Автоматическая пересборка и публикация при каждом push в `main`.

### Изменения

- **`.github/workflows/deploy-pages.yml`** — новый workflow: `npm ci` →
  `npm run check` → `vite build` (с `VITE_BASE=/Kalkuliator-nariezchika-iOS/`) →
  SPA-fallback `cp index.html 404.html` → публикация `dist/public` на Pages.
  Триггер — push в `main` и ручной запуск.
- **`vite.config.ts`** — `base: process.env.VITE_BASE ?? "/"` (env-gated;
  по умолчанию `/`, для Pages — под-путь проекта).
- **`client/src/App.tsx`** — маршрутизатор обёрнут в `<Router base>` wouter,
  база берётся из `import.meta.env.BASE_URL` (в dev/корне — `""`, поведение не
  меняется; под Pages — `/Kalkuliator-nariezchika-iOS`), чтобы ссылки и
  навигация работали из под-пути.
- **`client/public/manifest.webmanifest`** — `start_url`/`scope`/иконка
  переведены на относительные пути (`./`) — корректны и в корне, и в под-пути.

### Проверка (эмуляция GitHub Pages + Chromium/Playwright)

Статический сервер, повторяющий поведение Pages (под-путь + отдача `404.html`
для прямых ссылок), + headless Chromium: главная (HTTP 200, React смонтирован,
ресурсы без 4xx, консоль чистая); прямые ссылки `/warehouse`, `/reports`,
`/settings` (SPA-fallback → приложение поднимается, wouter сопоставляет
под-путь); in-app навигация wouter формирует URL с учётом base — **все проверки
пройдены**. `tsc` — 0 ошибок; сборки корневая и под-путь — обе успешны, без
предупреждений; движок расчёта идентичен `main`.

### Действие владельца (однократно)

Включить Pages: **Settings → Pages → Build and deployment → Source: GitHub
Actions**. После этого каждый push в `main` публикует приложение автоматически.

## Версия 2.0 — Интеллектуальная система управления производством

> Приложение из системы **учёта** становится системой **поддержки принятия
> решений**: анализирует накопленные данные, предупреждает оператора и советует.
> Архитектура не сломана; все новые функции построены на **существующих**
> моделях и на едином агрегаторе `ReportContext`/`ReportRepository`. Движок
> расчёта не изменён (байт-в-байт идентичен `main`); циклов зависимостей нет.

### Главное

Добавлен модуль `intelligence/` (v2.0) — «мозг» приложения поверх существующих
данных: центр уведомлений, прогнозирование, контроль качества, рекомендации,
глобальный поиск, история изменений настроек и архитектура интеграций. Все
движки — **чистые функции** над `ReportContext` (как `KpiEngine`), без доступа к
хранилищу и без пересчёта истории; результат кэшируется по сигнатуре данных.

### Структура модуля

```
intelligence/
├── models/        Notification, Forecast, Quality, Recommendation, Search, SettingsChange
├── engine/        NotificationEngine · ForecastEngine · QualityEngine · RecommendationEngine (чистые)
├── services/      IntelligenceService (оркестрация+кэш) · SearchService · SettingsHistoryService
├── integrations/  IntegrationProvider (ERP/1С/SAP/REST/CSV — протоколы-заготовки)

```

### Новые модели

- **AppNotification** (`NotificationKind`, `NotificationSeverity`
  Critical/High/Medium/Low, `NotificationStatus` new/seen/done) — уведомление с
  датой, описанием, рекомендуемым действием и статусом; **детерминированный id**
  (`kind:subject`), чтобы статус переживал перегенерацию.
- **ForecastResult** (`JumboForecast`, `MaterialForecast`, `LoadForecast`).
- **QualityReport** (`QualityMetric`, `QualityDimension`, флаг `anomaly`).
- **Recommendation** (`RecommendationKind`).
- **SearchHit / SearchResults** (`SearchResultKind`).
- **SettingsChangeEntry** — запись журнала изменений настроек.
- **IntegrationProvider / IntegrationInfo** (`IntegrationKind`,
  `IntegrationDirection`).

### Новые экраны

- **Центр уведомлений** (`/notifications`) — авто-предупреждения с бейджами
  важности/статуса, рекомендуемым действием и управлением статусом.
- **Центр решений** (`/decisions`) — прогнозы, контроль качества (с
  переключением разрезов и подсветкой аномалий) и рекомендации.
- **Глобальный поиск** (`/search`) — по Джамбам, заказам, материалам,
  операторам, документам и архиву, сгруппированный по типу.
- **История изменений** (`/settings/history`) и **Интеграции**
  (`/settings/integrations`) — в хабе настроек.
- Быстрый доступ добавлен на Dashboard.

### Центр уведомлений

`NotificationEngine` — набор **чистых правил** над агрегированными данными,
пороги настраиваются (по умолчанию разумные), учитывается пользовательский
`jumboThresholdM`. Правила: низкий остаток Джамба (<порога → High, <½ порога →
Critical); материал заканчивается/закончился на складе; высокий процент отходов;
длительное отсутствие активности по Джамбу (>14 дн.); ошибки отправки отчётов;
устаревшая/отсутствующая резервная копия; превышение уровня потерь. Каждое
уведомление имеет важность, дату, описание, рекомендуемое действие и статус;
статус (new/seen/done) сохраняется по детерминированному id, остальное
пересчитывается из данных.

### Алгоритмы прогнозирования

Прозрачные экстраполяции наблюдаемых средних (без скрытых моделей):

- **Окончание Джамба**: `средний расход/заказ = usedLength / ordersCount`;
  `заказов осталось = ⌊остаток / расход-на-заказ⌋`; дата = `now + заказов ×
  среднее-число-дней-на-заказ` (`окно / всего заказов`).
- **Расход материала**: `средний расход/день = Σ used_length_m / дни-окна`.
- **Запас склада**: `дней хватит = суммарный остаток / расход-в-день`.
- **Потребность в Джамбах (30 дн.)**: `⌈(расход/день × 30 − остаток) /
  средняя-намотка⌉`.
- **Загрузка станков/операторов**: доля заказов + проекция на 30 дней по темпу.

### Контроль качества и рекомендации

`QualityEngine` считает долю отходов по материалам/операторам/станкам (из
`result.waste_area_m2`, атрибутированного сессиям) и технологический остаток по
материалам (из архива), помечая аномалии (доля выше max(порог, 1.5×среднего)).
`RecommendationEngine` выводит советы из уведомлений/прогнозов/качества:
подготовить Джамб, заказать материал, проверить станок, запланировать
обслуживание, проверить качество сырья.

### Поиск, история настроек, интеграции

- **Поиск** читает существующие репозитории один раз и фильтрует в памяти
  (5000 Джамбов — ~20 мс), результаты ограничены по категориям.
- **История настроек** — `SettingsHistoryService` фиксирует каждое изменение

## Финальный аудит — независимая приёмка перед запуском производства

> Аудит выполнен как внешним техническим аудитором: код **не считался
> правильным только потому, что уже написан**. Проверены логика, математика,
> данные, безопасность и UX. Инвариант проекта сохранён: движок расчёта
> (`core/calculator/calculatorLogic.ts`) **не изменён** — байт-в-байт идентичен
> `main`. В отличие от предыдущих этапов, найденные дефекты **исправлены**.

### Найденные проблемы и критичность

**Critical:** не обнаружено.

**High**

- **H1. Удаление сессии из истории рассинхронизировало склад.**
  `useHistoryViewModel.remove/clearAll` вызывали «сырое»
  `cuttingSessions.delete`, оставляя накопители Джамба (использованная длина,
  рулоны, заказы, эффективность) и, как следствие, отчёты и KPI считающими
  удалённый заказ; остаток не восстанавливался. → **Исправлено.**
- **H2. Удаление материала без проверки ссылок.** Материал можно было удалить,
  даже если на него ссылаются Джамбы (активные или архивные), что создавало
  «сиротские» записи. → **Исправлено.**

**Medium**

- **M1. Настройка `jumboThresholdM` игнорировалась.** Экран «Производство»
  позволял задать порог перевода в списание, но `WarehouseService` использовал
  константу 300 и настройку не читал — интерфейс вводил в заблуждение. →
  **Исправлено.**
- **M2. Нарушение MVVM.** `MaterialEditorView` вызывал `repository.delete`
  напрямую, минуя ViewModel. → **Исправлено** (логика удаления перенесена во
  ViewModel).

**Low**

- **L1. `confirmDelete` — декоративная настройка.** Все опасные действия и так
  подтверждаются диалогом `AlertDialog` независимо от флага; риска потери
  данных нет. → Требует решения владельца (связать флаг или убрать).
- **L2. `rollbackTransaction` без вызовов** (латентный публичный API).
  Оставлен как легитимная возможность отмены транзакций; задокументирован.

### Что исправлено автоматически

1. **`WarehouseService.deleteSession(sessionId)`** — новая атомарная операция:
   восстанавливает накопители и остаток исходного Джамба ровно на величину
   удаляемого заказа, затем удаляет сессию и её операции. Архивированный Джамб
   (замороженный снимок) не мутируется. История удаления теперь консистентна
   для склада, отчётов и KPI. `useHistoryViewModel.remove/clearAll` переведены
   на него.
2. **Референс-гард удаления материала** — `useMaterialEditorViewModel.remove()`
   блокирует удаление материала, на который ссылаются Джамбы (активные или
   архивные), с понятным сообщением («переведите в архив»). Экран показывает
   предупреждение вместо порчи данных.
3. **Учёт `jumboThresholdM`** — `WarehouseService` получает
   `SettingsRepository` и читает порог из настроек (по умолчанию 300 м) в
   `completeCalculation`, `rollbackTransaction` и `deleteSession`. Поведение по
   умолчанию не изменилось; настройка стала рабочей.
4. **MVVM** — удаление материала инкапсулировано во ViewModel; View вызывает
   `vm.remove()`.

Движок расчёта не тронут; предупреждений компилятора нет; дублирование не
внесено (переиспользована существующая логика реверса накопителей).

### Что требует решения владельца продукта

- Допустимо ли операторам вообще удалять производственные записи (сессии)?
  Теперь это безопасно и консистентно, но практика MES часто запрещает
  деструктивные изменения истории — возможно, стоит заменить удаление на
  «отмену» (`rollbackTransaction` уже готов) с сохранением записи.
- Связать настройку `confirmDelete` с поведением или убрать её.
- Платформенные решения: `localStorage` vs промышленная БД; симулированный
  e-mail vs реальный шлюз; печатный HTML vs бинарный PDF.

### Улучшенные архитектурные решения

- Целостность истории вынесена в сервисный слой (`deleteSession`), а не в
  ViewModel — единый источник правды для мутаций склада.
- Порог списания стал конфигурируемым через единый слой настроек (DI), без
  «магической» константы в бизнес-операции.
- Устранена утечка слоёв (View → репозиторий) в пользу MVVM.

### Масштабируемость

Точки роста прежние и подтверждены: сменный `StorageProvider`
(localStorage → IndexedDB/облако) без изменения вышележащих слоёв; реестры
построителей отчётов, провайдеров экспорта/e-mail; роли пользователей; чистый
`KpiEngine`. Нагрузка подтверждена ранее (1000 Джамбов, 100 000 операций —
доли секунды).

### Остаточные риски

- `localStorage` ограничен по объёму (браузер) — для многолетних объёмов
  рекомендован переход на IndexedDB (интерфейс готов).
- E-mail — симуляция; PDF — печатный HTML; рассылка по расписанию — при
  запуске приложения. Всё задокументировано, не блокирует эксплуатацию.
- `receiveBatch` ~O(n²) на очень больших единичных партиях (незаметно для
  реальных приёмок).

### Верификация исправлений

- Порог: высокий `jumboThresholdM` (4500) переводит Джамб в списание выше

- Математика: `usedLength = начальная намотка − остаток`;
  `efficiency = полезная площадь / обработанная площадь`.

  сессии и её операций, консистентность KPI (заказы 3→2), полный возврат
  Джамба к исходному состоянию после удаления всех сессий, no-op для
  неизвестного id, целостность после операций.
- Референс-гард материала: занятый материал определяется, свободный — удаляем.

### Хранилище как протокол (`StorageProvider`)

Всё приложение уже персистит через `KeyValueStore` — значит, **это и есть**
протокол провайдера хранения. Локальный провайдер активен; облачный
(iCloud/CloudKit/Firebase/собственный сервер) — заготовка, реализующая тот же
интерфейс. Переключение бэкенда не затрагивает бизнес-логику.

### Резервное копирование и восстановление

`BackupService` снимает единый JSON-снимок всех коллекций
(`backupStorageKeys`): Джамбы, материалы, сессии, операции, потери, архив,
документы, журналы, пользователи, настройки. `restore()` записывает их обратно
(с проверкой версии копии), `exportJson()/importJson()` работают с файлом
(скачивание через Blob, импорт через `FileReader`), `isBackupData` защищает от
некорректного ввода. Каждое копирование/восстановление фиксируется в аудите,
метки времени хранятся в `backupMeta`.

### Обслуживание базы

`MaintenanceService.scan()` — единая проверка связей: у Джамба существует
`materialId`; остаток в диапазоне `[0; initialWinding]`; `session.jumboId`,
`operation.jumboId`, `waste.jumboId` указывают на существующий Джамб (активный
или архивный). `checkIntegrity()` возвращает полный отчёт, `checkRelations()`
— только нарушения связей. `optimize/rebuildIndexes/clearCache` для локального
хранилища — безопасные операции с честным описанием (индексы для KV-хранилища
не требуются). Проверки **только читают** данные; все действия аудируются.

### Журналы и диагностика

- **Журнал ошибок**: глобальный обработчик (`useAppBootstrap`) ловит
  `window.onerror` и `unhandledrejection` и пишет в `errorLog` (описание, стек,
  версия). Экран журналов показывает ошибки и аудит с переключением и очисткой.

- **Диагностика**: версии приложения и БД (`DB_VERSION`), счётчики записей,

### Формулы показателей

- `materialUsedM = Σ session.result.used_length_m`
- `usefulAreaM2 = Σ session.result.useful_area_m2`
- `processedArea = Σ (materialWidthMm/1000 × used_length_m)`
- `avgUsagePercent = usefulArea / processedArea × 100`
- `waste/scrap/totalLosses = Σ` замороженной статистики архива за период
- `avgPerOrderM = materialUsedM / orders`; `avgPerRollM = materialUsedM / rolls`
- Джамбы: `avgAreaM2 = avg(initialWinding × width/1000)`,
  `avgRemainderM = avg(остаток)`, `avgUsagePercent = avg(efficiency)`
- Станок: `productivity = rolls / hours`
- Сравнение: `deltaPercent = (current − previous) / previous × 100`
- Тренд: суммы по бакетам `bucketLabel(createdAt, grouping)`

### Архитектура PDFBuilder

```ts
interface PDFBuilder { build(report: ReportData, options?): PdfDocument }
```

Получает **только `ReportData`**, не обращается к хранилищу и не считает.
Все 7 типов отчётов проходят через единый `PdfTemplate` (логотип, название,


`EmailTransport` — единственная точка расширения для реальной доставки

`id (UUID)`, `title`, `kind`, `createdAt`, `periodLabel`, `recipients[]`,

`automatic`, `sentAt?`. **Повторная отправка использует сохранённый документ**

### Ручная и автоматическая отправка

- **Ручная**: экран «Новый документ» — выбор типа отчёта, периода и получателей,

Неудачная отправка сохраняет статус `Ошибка` и текст ошибки; из истории или
карточки документа доступна повторная отправка.

## Этап 4 — Полный жизненный цикл Джамба

> Платформа та же (React + TS + Vite); «SwiftData» — слой репозиториев над
> `KeyValueStore`. **Алгоритм расчёта нарезки не изменён** (движок идентичен
> `main`).

### Главное

Реализован полный жизненный цикл Джамба: поступление → в работе → подлежит
списанию → **закрытие** → архив. При закрытии остаток списывается как
технологический остаток, итоговые показатели вычисляются **один раз** и
замораживаются в архиве.

### Жизненный цикл и закрытие Джамба

1. **Действие «Закрыть Джамб»** на карточке Джамба со сводкой перед закрытием
   (номер, материал, начальная намотка, остаток, использовано, полезная
   площадь, количество заказов, количество рулонов).
2. **Технологический остаток.** Остаток автоматически становится записью
   `Waste` типа «Технологический остаток» (метры, м², дата, оператор,
   комментарий).
3. **Итоговые показатели** (замораживаются в архиве, больше не меняются):
   общая площадь, полезная площадь, площадь брака, площадь тех. остатка,
   общие потери, % полезного использования, % брака, % тех. потерь + метраж,
   заказы, рулоны, операции, коэффициент.
4. **Архивирование.** Статус → «Архив», операция журнала `Archive`, создаётся
   `ArchivedJumbo` — самодостаточный снимок: финальный Джамб, история операций,
   история заказов (`CuttingSession[]`), история потерь (`Waste[]`), итоговая

## Этап 3 — Интеграция расчёта нарезки со складом

> Платформа та же (React + TS + Vite). «SwiftData» — слой репозиториев над
> `KeyValueStore`. **Математический алгоритм расчёта нарезки не изменён** —
> движок вызывается с теми же аргументами; изменена только производственная
> логика вокруг расчёта.

### Главное

- Каждый производственный расчёт теперь выполняется по конкретному Джамбу:
  оператор заполняет информацию о заказе, выбирает Джамб вручную, после
  успешного расчёта остаток и накопительные показатели Джамба обновляются
  инкрементально, создаётся операция журнала и сессия истории, Dashboard
  показывает актуальные данные.
- Свободный калькулятор (Этап 1) сохранён как «Быстрый расчёт» — те же
  результаты, без списания со склада.

### Новая логика расчёта и её связь со складом

1. Экран **«Производство»**: карточка «Информация о заказе» (дата, время,
   заказчик, номер заказа, оператор, станок №1/№2, комментарий).
2. Кнопка **«Выбрать Джамб»** открывает список доступных Джамбов (без
   авто-выбора/FIFO). Выбранный Джамб показывается в блоке «Используемый Джамб»
   только для чтения.
3. Материал берётся из выбранного Джамба: ширина материала = ширина Джамба,
   доступная длина = текущий остаток Джамба. Расчёт считается тем же движком.
4. Перед расчётом проверяется: выбран Джамб; остаток > 0; статус ≠ «Подлежит
   списанию»; материала достаточно. Если нет — показывается сообщение
   «Недостаточно материала…», расчёт не выполняется.
5. Первое использование Джамба: дата начала использования, статус «В работе»
   (жёлтый), операция `usageStart`.
6. После выполнения `WarehouseService.completeCalculation` **инкрементально**:
   уменьшает остаток, увеличивает `usedLength`, `usefulArea`, `ordersCount`,
   `rollsCount`, пересчитывает `efficiency` (из накопителей, не по истории),
   создаёт `JumboOperation` типа `calculation` и `CuttingSession`.
7. Если остаток < 300 м — статус «Подлежит списанию» (красный) и уведомление;
   такой Джамб исключается из выбора для новых расчётов.

### Автоматически обновляемые накопительные показатели (в записи Джамба)

`currentRemainderM`, `usedLength`, `usefulArea`, `ordersCount`, `rollsCount`,
`efficiency`. История никогда не пересчитывается целиком.

### Транзакционная модель, откат и версионирование (доп. к Этапу 3)

- **Атомарная транзакция.** `completeCalculation` выполняется как одна
  транзакция с общим `transactionId`: при ошибке частичные записи
  откатываются (снимок Джамба восстанавливается, созданные операции/сессия
  удаляются), состояние остаётся согласованным.
- **`rollbackTransaction(transactionId)`** в `WarehouseService`: восстанавливает
  остаток, уменьшает `usedLength / usefulArea / ordersCount / rollsCount`,
  пересчитывает `efficiency`, помечает операции `isReverted = true`, а сессию —
  `status = reverted`. **Записи не удаляются** — история неизменяема. UI отката
  на этом этапе не создаётся (по требованию).
- **Версионирование.** `CuttingSession.version` (всегда 1) + `transactionId`,
  `status`, `createdAt`, `updatedAt`; архитектура готова к будущим версиям
  заказа и хранению предыдущих версий.
- **Расширен `JumboOperation`:** `transactionId`, `sessionId`, `createdAt`,
  `updatedAt`, `isReverted` (+ производственный контекст из основной части).
- **Проверка сценариев.** Прогонян отдельный harness (in-memory store):
  новый заказ, повторный заказ, первый запуск, `< 300 м → «Подлежит списанию»`,
  недостаточный остаток, создание сессии/журнала, откат с восстановлением
  накопителей и неизменяемой историей — 32/32 проверки пройдены. Harness не
  коммитится.

### Поток Repository → Service → ViewModel → View

```

  → ViewModel (useProductionViewModel)  — состояние формы, live-план, валидация
    → Service (WarehouseService.completeCalculation / rollbackTransaction,
               CalculationService.calculate)
      → Repository (Jumbo / JumboOperation / CuttingSession)
        → Storage (KeyValueStore)
```

ViewModel никогда не обращается к хранилищу напрямую — только через сервисы и
репозитории.

### Архитектурные решения

- **Repository-only мутации.** Все изменения проходят через репозитории;
  производственная логика — в `WarehouseService.completeCalculation`, ViewModel
  не пишет в хранилище напрямую.
- **Инкрементальные накопители.** Показатели обновляются как дельты к полям
  записи Джамба; полные пересчёты истории исключены (O(1) на операцию).
- **Разделение потоков.** Свободный калькулятор и производственный расчёт
  используют один и тот же `CalculationService`, но разные ViewModel/экраны
  (SRP): математика едина, производственная обвязка изолирована.
- **`CuttingSession` — единая сущность истории производства**, объединяющая
  заказ, Джамб, рулоны, операции и (в будущем) брак.
- **Кнопка «Добавить брак»** добавлена только как интерфейс (без логики) —
  фундамент для Этапа 4.

| Группа | Назначение |
| --- | --- |

| `repositories/` | Протокол репозитория и реализации (не зависят от UI) |
| `storage/` | Заменяемый слой хранения (`KeyValueStore` + `localStorage`) |
| `viewmodels/` | По одному ViewModel на каждый экран (MVVM) |
| `views/` | Экраны (только из переиспользуемых компонентов) |
| `components/` | Библиотека UI-компонентов |

Принципы: SOLID, DRY, KISS, композиция вместо наследования, Dependency
Injection (единый composition root в `core/di/container.ts`), протокол-
ориентированный дизайн (`Repository`, `*Service`), `async/await` в сервисах и
репозиториях. Бизнес-логики внутри View нет — каждый экран работает только со
своим ViewModel.

## Подготовка к следующим этапам

- **Склад Джамбов.** Модель `Jumbo` хранит поля учёта и аналитики: номер
  складского учёта, код материала, ширина, начальная намотка, текущий остаток,
  общий использованный метраж, полезная площадь, накопленный брак, накопленные
  технологические остатки, коэффициент использования, даты поступления / начала
  / окончания использования, статус.
- **Инкрементальный учёт.** Накопительные значения хранятся прямо в записи
  Джамба, а модель `JumboOperation` фиксирует дельты каждой операции. Это
  заложено так, чтобы после каждой операции остаток и показатели обновлялись
  инкрементально, а не пересчитывались по всей истории.
- **Статусы.** `JumboStatus` (На складе / В работе / Подлежит списанию / Архив)
  с цветовой схемой (обычный / жёлтый / красный / серый) через `StatusBadge`.
- **Аналитика (KPI).** Подготовлены модели `MaterialStatistics`,
  `MachineStatistics`, `OperatorStatistics`, `WasteStatistics`,
  `ProductionStatistics` (структура без расчётов).
- **Отчёты.** `ReportService` — интерфейс + запись запроса без генерации PDF.
- **Email.** `EmailService` — API определён, реализация появится позже.
- **Хранение.** `Repository`-протокол и заменяемый `KeyValueStore` позволяют
  перейти на другое хранилище (сервер / IndexedDB / SwiftData-эквивалент) без
  изменений в ViewModel и View.
