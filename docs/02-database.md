# 2. База данных

## Модель хранения

Персистентность абстрагирована интерфейсом `KeyValueStore`
(`read/write/remove`). Активная реализация — `LocalStorageStore` поверх
`window.localStorage`; данные сериализуются в JSON. Каждая доменная коллекция
живёт под своим ключом (`storage/StorageKeys.ts`), в native-терминах это
эквивалент таблиц SwiftData.

| Ключ | Коллекция |
| --- | --- |
| `narezka.store.materials` | Материалы |
| `narezka.store.jumbos` | Джамбы (активные) |
| `narezka.store.jumboOperations` | Операции над Джамбами |
| `narezka.store.cuttingSessions` | Производственные сессии (заказы) |
| `narezka.store.wastes` | Потери (брак / тех. остаток) |
| `narezka.store.archivedJumbos` | Архив закрытых Джамбов (снимки) |
| `narezka.store.documents` | Сформированные документы (PDF/e-mail) |
| `narezka.store.documentsMeta` | Метаданные планировщика документов |
| `narezka.store.errorLogs` | Журнал ошибок |
| `narezka.store.auditLogs` | Журнал аудита |
| `narezka.store.users` | Пользователи |
| `narezka.store.backupMeta` | Метки резервного копирования |
| `narezka.store.settings` | Настройки приложения |

`backupStorageKeys` перечисляет коллекции, входящие в полный снимок резервной
копии и диагностический подсчёт.

## Репозитории и запросы

Доступ к данным идёт только через `CollectionRepository<T>`
(`getAll/getById/save/delete/clear`). Запрос — это загрузка коллекции и
фильтрация в памяти; для объёмов производственного участка (тысячи Джамбов,
сотни тысяч операций) это быстро (см. [отчёт по производительности](#производительность-запросов)).

## Отношения

- `Jumbo.materialId → Material.id` (многие-к-одному).
- `Jumbo.materialCode` — денормализованный код материала для быстрого поиска.
- `JumboOperation.jumboId → Jumbo.id`; опционально `sessionId → CuttingSession.id`,
  `transactionId` группирует операции одной атомарной записи.
- `CuttingSession.jumboId → Jumbo.id`.
- `Waste.jumboId → Jumbo.id` (опционально).
- `ArchivedJumbo` — самодостаточный **снимок**: содержит финальную копию
  `jumbo`, свои `sessions/operations/wastes` и замороженную `statistics`.

## ER-диаграмма

```
              ┌───────────────┐
              │   Material    │
              │  id (PK)      │
              │  code (uniq)  │
              └──────┬────────┘
                     │ 1
                     │        materialId (FK)
                     │ N
              ┌──────┴────────┐        1      N ┌────────────────┐
              │    Jumbo      │─────────────────│ JumboOperation │
              │  id (PK)      │  jumboId (FK)    │  id (PK)       │
              │  materialId   │                  │  jumboId (FK)  │
              │  stockNumber  │                  │  sessionId?    │
              │  status       │                  │  transactionId?│
              └──┬─────────┬──┘                  └────────────────┘
              1 │         │ 1
                │ N       │ N
      ┌─────────┴───┐ ┌───┴──────────┐
      │CuttingSession│ │    Waste     │
      │ id (PK)      │ │  id (PK)     │
      │ jumboId (FK) │ │  jumboId?    │
      │ order,result │ │  kind, area  │
      └──────────────┘ └──────────────┘

   При закрытии Джамба формируется снимок:
              ┌──────────────────────────────────┐
              │        ArchivedJumbo             │
              │  id (PK)                         │
              │  jumbo (снимок)                  │
              │  sessions[] operations[] wastes[]│
              │  statistics (заморожена)         │
              └──────────────────────────────────┘

   Служебные (администрирование):
   User(id)   ErrorLogEntry(id)   AuditEntry(id)   Settings   BackupMeta
```

## Индексы

Отдельных индексов у key-value хранилища нет; роль индекса выполняют
денормализованные поля (`materialCode`, `stockNumber`) и накопительные
счётчики Джамба, дающие O(1)-чтение без пересчёта истории. Для перехода на
IndexedDB (см. Roadmap) индексы добавляются в реализации `KeyValueStore` без
изменения вышележащих слоёв.

## Целостность данных

- **Транзакционность записи**: `WarehouseService.completeCalculation`
  выполняется как одна атомарная транзакция с `transactionId` и возможностью
  `rollbackTransaction`; частичные записи откатываются.
- **Замороженные аккумуляторы**: статистика Джамба и архива хранится прямо в
  записи и никогда не пересчитывается воспроизведением истории.
- **Проверки связей**: `MaintenanceService.scan()` находит битые ссылки
  (материал Джамба, `jumboId` сессий/операций/потерь) и аномалии остатка
  (`0 ≤ остаток ≤ намотка`). Экран «Обслуживание» показывает отчёт.

## Обновление моделей и миграции

Версия схемы — `DB_VERSION` (`admin/services/DiagnosticsService.ts`),
версия формата копии — `BACKUP_VERSION`. Модели расширяются **аддитивно**
(новые опциональные поля), что сохраняет обратную совместимость со старыми
записями. Механизм миграций по `DB_VERSION` заложен и включается при первом
несовместимом изменении (см. Roadmap).

## Устойчивость к повреждениям

`LocalStorageStore.read` оборачивает `JSON.parse` в try/catch и возвращает
`undefined` при повреждённом значении — одна испорченная запись не роняет
приложение. Ошибки отрисовки перехватывает `ErrorBoundary`, необработанные
ошибки/reject — глобальный обработчик; всё пишется в журнал ошибок.

## Производительность запросов

Замер на in-memory хранилище (1000 Джамбов + 100 000 операций):

| Операция | Время |
| --- | --- |
| Диагностика (счётчики + размер БД по всем ключам) | ~0,2 с |
| Проверка целостности (полный `scan`) | ~0,1 с |
| Резервная копия (снимок всех коллекций) | ~0,1 с |
| Большой отчёт (2000 архивных Джамбов) | ~0,01 с |

Известная особенность: пакетный приём `receiveBatch` имеет сложность ~O(n²)
по размеру одной партии (перезапись коллекции на элемент). Для реальных
партий (единицы–десятки Джамбов) незаметно; массовый импорт тысяч записей за
один вызов следует делать через прямую запись коллекции.
